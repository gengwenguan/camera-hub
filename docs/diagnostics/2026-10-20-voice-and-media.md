# MI6 语音与媒体链路排查

环境：MI6 / Android 9，camera-hub APK，V831 摄像头；2026-10-20 实测。

## 结论与证据边界

排查发现两个独立、可复现的问题：APK 后台恢复遗漏麦克风恢复，以及 Android FFmpeg 的 fMP4 复用只有视频持续输出。
修复版本为 Android 0.5.12。现有固定短语、关键词阈值、设备控制地址、密码和业务配置保持不变。

用户最初反馈发生时，语音状态是 `listening`，不能据此断言当时一定发生了后台恢复问题。
最初那次真实口述没有保留录音，无法复现具体距离、音量和环境噪声。以下区分已复现缺陷、受控测试和仅状态检查。

## 1. 后台恢复服务未恢复麦克风

### 复现

在 MI6 覆盖安装旧版 APK，不打开界面。服务通过 `RESTORE` 重新启动，HTTP 健康接口正常，但语音不断进入 `audio-error`。
直接请求 Android 硬件桥接采集返回：

```json
{"ok": false, "error": "后台恢复后需在 App 中点击「恢复语音」"}
```

录音运行时权限和 AppOps 均已允许。故障来自应用自身的采集门禁，不是灯控 HTTP 地址、KWS 模型文件或 Android 拒绝录音。
`EngineService` 原先只在手动启动时启用麦克风，把较新 Android 的后台录音限制也应用到了 MI6 的 Android 9。
精简首页没有恢复入口的自动处理，用户打开首页也不能解除该门禁。

### 修复

- Android 8–10：已获得录音权限时，恢复前台服务同时恢复麦克风。
- Android 11+：保留后台录音限制；用户打开已解锁的 App 页面时自动申请恢复已有服务的麦克风资格。
- 仅处理已运行服务；不会因为打开首页重新启动用户已手动停止的服务。
- 保留“授权 / 恢复语音”的手动入口，更新后台说明。

### 语音链路验证

先验证灯控 HTTP 请求，再将中文“小雨开灯”“小雨关灯”样本通过 MI6 扬声器播放，由 MI6 的真实麦克风采集，经原有 KWS 和命令执行链处理。
这不是直接向 KWS 注入 PCM，也不是仅调用命令测试接口。

| 检查 | 观测 |
| --- | --- |
| 灯控 HTTP | 开、关请求均返回 200；直接请求耗时约 36 / 21 ms |
| 真实采集 + KWS | 两个命令均产生 `source=voice`、`success=true`、HTTP 200 的事件 |
| 回复和恢复 | 命令事件约 3.3 秒，包含缓存回复播放；随后恢复 `listening` |
| 按需 ASR | 限时录音得到新的“开灯”转写，随后恢复监听 |
| 新文本 TTS | “语音检查完成。”生成有效 24 kHz 单声道 WAV，时长 1.52 秒，首次合成约 35.93 秒 |
| 新系统兼容 | Android 15 模拟器覆盖安装后先恢复非麦克风前台服务；打开首页后取得麦克风服务类型 |

MI6 上全新 TTS 文本仍由 CPU 合成，速度慢于缓存回复；不能把它用于需要即时反馈的任意新句子。
此测试验证识别、执行请求、返回结果及播放链路，不提供灯具物理状态反馈，也不能代表所有人的发音和远场识别率。

## 2. fMP4/MSE 等待媒体，录像音频没有持续写入

### 复现与定位

HTTP-FLV 和 WebRTC 在浏览器中可以连续播放。fMP4/MSE 虽已收到初始化数据、解析出 640×480 视频信息，却没有完整音视频缓冲。
仅检查 `ftyp` / `moof` 或录像字节增长会漏掉这个问题。

- 实时 WebSocket 抓取的 12 秒 fMP4：360 个可解码 H.264 帧，没有 AAC 数据包。
- 同时获取的 FLV：存在数百个 AAC 包，说明摄像头音频上传正常。
- 修复前正在生成的一段约 681 秒录像：20,437 个视频包，但仅有最初的一个 AAC 包。
- FFmpeg 的 AAC UDP 接收队列积压并丢包；上游仍在发送。
- 用 APK 内同一个 FFmpeg 7.1.2 处理有限 H.264/AAC 文件，前面的片段同样只有视频，音频主要在视频输入结束后才输出。

原始 H.264 输入没有 DTS。FFmpeg 7 的调度器先根据输入时间戳决定读取哪个流，stream-copy 后续才补算视频 DTS。
音频已有时间戳，视频没有，导致音频输入被调度器阻塞。无限直播输入不能依靠文件结束来解除这个状态。
单独指定 `-r 30` 可以让视频片段增长，但不足以保证音频公平进入复用。

### 修复

在 Android 的 H.264 **输入侧**增加 bitstream filter：

```text
-r 30 -bsf:v setts=ts=N/(30*TB):duration=1/(30*TB) -f h264 -i ...
```

在进入调度器之前，按当前摄像头链路已有的 30 fps 约定生成 PTS、DTS 和时长。继续复制压缩数据，不增加视频转码负载。
Android 内置 FFmpeg 显式启用 `setts`，已有缺少该 filter 的构建缓存会重新配置、编译。
LinuxDeploy 的 FFmpeg 4.2 不支持输入侧 BSF，保留其原有路径；本次改动不升级或启用旧 LinuxDeploy 服务。

在有限样本的逐片段检查中，修正后的每个完整 1 秒片段同时具有 30 个视频样本及约 47 个音频样本。
新增环境检查会要求实时 fMP4 的两条轨道都持续提供样本，避免再次出现“有录像文件就算健康”的误判。
修复不会补回此前没有录下的历史音频。

## 验证范围

- 用户告知休息后，停止一切灯控、录音、语音合成与播放测试；后续仅执行静默读取和验证，不再次安装或重启正式服务。
- 已实际执行：APK 覆盖安装恢复、受控语音灯控、ASR、缓存回复、新文本 TTS、摄像头上传、录像增长与读取、实时媒体传输、浏览器登录。
- 已检查运行状态：DDNS、QQ Gateway、IR 硬件、模型资源。没有发送 QQ 消息、开门命令或空调红外指令。
- MoQ 当前配置为关闭，接口无启动错误；不把它计为已完成端到端播放。
- AI 相册接口可用，但相册当时为空，不能据此验证已有照片浏览。
- 不把短时检查等同于长时间稳定性或任意网络、噪声条件下的保证。
